# MemoX V8 CI Gate Implementation Plan (package 6)

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build BE-D2 of [`docs/wbs_BE.md`](../../wbs_BE.md): a GitHub Actions
workflow that runs the verification gate and the golden comparison on Linux for
every pull request, with one check to require, `CI gate`, green only when every
other job succeeded.

**Architecture:** `.github/workflows/ci.yml` has three jobs. `gate` rebuilds the
generated code from scratch (`check_generated.py`) and runs the local gate,
`dod_check.sh`, in full. `goldens` runs `flutter test --tags golden` with a JSON
file report beside the console, and counts that report against a floor of 60
(`count_golden_tests.py`). `CI gate` waits for both, runs whatever happened to
them, prints each result and fails unless both succeeded. The CI tooling tests,
which run inside the gate, pin that contract by reading the workflow as text.
V7's shard and aggregate-gate scripts, which nothing in V8 uses, go.

**Tech Stack:** GitHub Actions on `ubuntu-latest` (`actions/checkout@v7`,
`actions/setup-python@v7`, `subosito/flutter-action@v2`,
`actions/upload-artifact@v7`, `jq` on the runner); Python 3 `unittest` for the CI
tooling tests; Flutter 3.47.5 from `.fvmrc`. The app gains no dependency.

**Spec:** [`docs/superpowers/specs/2026-09-25-ci-gate-design.md`](../specs/2026-09-25-ci-gate-design.md),
approved 2026-09-25 and amended on this branch with the Clarifications below.

**Prerequisite:** `claude/be-ci` holds the spec (`6811471`), its approval
(`c799e22`) and its amendment from the Clarifications below (`0f14c7d`), on
`master` at `fe5f32a` (#62). This plan runs on that branch, from the commit that adds it;
the gate passes there with 1450 host tests. Generated code is not committed: in
a fresh working tree, run `flutter pub get`, `flutter gen-l10n` and
`dart run build_runner build --delete-conflicting-outputs` first (root
`README.md`, "Commands"). Every command below runs from the repository root,
with this repository's Flutter on `PATH` (in Claude Code on the web,
`export PATH=/root/.flutter-sdk/3.47.5/flutter/bin:$PATH`).

**How this plan was checked:** every code block below was written and run in a
scratch copy of the repository, task by task, test first, and the gate passed
after every task. The rules the new tests pin were then broken on purpose, and
every break failed a test: the golden count's five rules (the floor, its bound,
a failed test, skipped tests, the reporter's loading entries), and sixteen
breaks of the workflow (`--fast` or `--changed` on the gate, the rebuild skipped
or gone, `--update-goldens`, a count reading another file, a floor of 0, no
count, a job that `CI gate` does not wait for, no `if: always()`, a `CI gate`
that judges nothing or passes on any success, a path filter, a push trigger, a
pinned Flutter version, a new job left out of `needs`). Both jobs then ran on
clean checkouts the way the runner runs them: `gate` with `CI=true`, no git
identity and PowerShell 7 on `PATH`, so the eight PowerShell tests ran too (77
CI tooling tests, none skipped); `goldens` with `CI=true`,
`GITHUB_ACTIONS=true` and `prepare_test_fonts.sh` on a copy of the SDK. Both
passed, and a broken host test and a broken golden turned each red, naming the
test. `actionlint` 1.7.12, with shellcheck 0.11.0, found nothing in either
workflow. This document was then applied, step by step as written, onto a
clean checkout of `c799e22`, whose tree differs from this plan's commit only in
the spec's amendment and in this document: each task's files matched the
scratch commit's, no other file moved, and the outputs below are that run's.

## Global Constraints

Every task's requirements implicitly include these.

- Scope: `.github/workflows/ci.yml`, the CI tooling it needs, the removal of the
  V7 CI tooling that nothing in V8 uses, and the documents. Not in scope: the
  planner's CI-only surface (BE-D5), release builds, signing, the web build,
  deployment, a post-merge run on `master`, coverage reports, and caching beyond
  `subosito/flutter-action`'s. `build-apk.yml` stays as it is (spec D1, §9).
- CI runs the local gate: `dod_check.sh` in full, never `--fast` or `--changed`,
  and `check_generated.py` without `--skip-rebuild` (spec D2, D5).
- Triggers: `pull_request` and `workflow_dispatch`; no path filter, no `push`.
  One concurrency group per pull request, cancelling the run in progress;
  `permissions: contents: read` (spec D4).
- Jobs: `gate` on `ubuntu-latest` with 30 minutes; `goldens` beside it with 20
  minutes and a floor of 60; `CI gate` with `if: always()` and `needs` naming
  every other job, green only when all of them succeeded. The workflow never
  contains `--update-goldens` (spec D5–D7).
- Every job that installs Flutter uses `subosito/flutter-action@v2` with
  `flutter-version-file: .fvmrc` and `cache: true` (spec D5, §5.2).
- The workflow's contract is tested by reading `ci.yml` as text, without PyYAML:
  the CI tooling tests run inside `dod_check.sh`, which installs nothing (spec
  §5.2).
- Kept: `build_verification_plan.py`, `check_generated.py`,
  `check_prompt_contract.py`, `prepare_test_fonts.sh`, `count_golden_tests.py`
  (spec D8).
- After every task the gate of the root `README.md` passes:
  `bash .claude/skills/flutter-workflow/scripts/dod_check.sh`.
- A script prints its messages in English (`CLAUDE.md`, "Language"); `docs/`
  keeps its Vietnamese; code, identifiers, test names and commit messages are in
  English. Every commit message ends with the session's attribution trailers.
- A pull request is merged only once `CI gate` is green on its head, after a
  clean final review (spec D3, D14).

## Clarifications to confirm during plan review

Writing and running the code settled what the spec left to the plan and showed
where it needed a change. Each is decided here, implemented as described, and
written into the spec on this branch; say so if one is wrong.

1. **The golden step keeps a readable log** (Task 3; spec §4, D6). The step runs
   `TZ=UTC flutter test --tags golden --file-reporter json:golden-report.jsonl`:
   the console keeps the runner's reporter, which names a failed golden
   (`❌ … MxErrorState with and without Retry (failed)`), and the JSON report goes
   to the file the count reads. A failed golden therefore stops the job at that
   step, red and named, and the failure images are uploaded. The count runs
   after a passing run, where it fails a run under the floor or a missing
   report; it still fails a report that holds a failed test (spec §5.3). The
   spec said `--reporter json` into a report and "`count_golden_tests.py`
   decides the job's result": a JSON-only console names nothing.
2. **Flutter 3.47.5 fails a run of no test** (Task 2). `flutter test --tags
   golden` that selects nothing prints `No tests ran.` and exits 79; the
   script's docstring said it exits 0. The floor still matters: a partial
   collapse, such as a golden file that lost its tag, passes. The docstring now
   says so.
3. **A missing report** (Task 2; spec §4). The script raised
   `FileNotFoundError` with a traceback; it now prints
   `::error::cannot read the golden report <path>: No such file or directory`
   and exits 1.
4. **Tests of rules the script already has** (Task 2; spec §7). Five of the six
   golden count tests pin rules `count_golden_tests.py` already has, so no
   change of this plan makes them pass. Step 3 breaks each rule in turn, watches
   its test fail, and restores the script with `git checkout`; the sixth test,
   the missing report, fails first and passes after Step 4.
5. **How `CI gate` judges** (Task 3; spec D7). Its one step reads
   `${{ toJSON(needs) }}`, prints `<job>: <result>` for every job it waits for,
   and fails unless all of them are `success` (`jq`, preinstalled on the
   runner). The contract requires `toJSON(needs)` beside §5.2's `if: always()`
   and `needs`, so a gate that judges nothing fails a test, and
   `test_ci_gate_is_green_only_when_every_job_succeeded` runs the step's own
   script on four sets of results (Review Focus 1). It needs `bash` and `jq`,
   and skips without them, as `DodCheckStampTest` skips without bash.
6. **A missing workflow fails the contract** (Task 3; spec D9). The tests it
   replaces skipped until `ci.yml` existed; V8's contract fails without it
   (`.github/workflows/ci.yml is missing: no pull request is verified`), so
   `requires_ci_workflow` goes.
7. **The fonts step** (Task 3; spec D6). In this repository's Linux container
   the 87 goldens pass with and without the lowercase font links that
   `prepare_test_fonts.sh` makes: the tests load the app's bundled fonts from
   `FontManifest.json`. The job keeps the step so that CI renders the way
   `golden.Dockerfile`, where the pictures are written, does. The step runs
   `flutter precache --force --universal`, which rewrites the SDK's artifacts,
   so the local run of the job's commands (Task 3, Step 7) leaves it out; the
   scratch run ran it on a copy of the SDK (10 s).
8. **Action versions** (Task 3; spec §10). The newest majors on 2026-09-25 are
   `actions/checkout@v7`, `actions/setup-python@v7`, `actions/upload-artifact@v7`
   and `subosito/flutter-action@v2`; `build-apk.yml` has run six times with
   `checkout@v7` and `flutter-action@v2`. `flutter-action` exports
   `FLUTTER_ROOT`, which `prepare_test_fonts.sh` reads, and with `cache: true` it
   caches the pub cache as well as the SDK.
9. **Documents beyond the spec's §6** (Tasks 3 and 4). `golden.Dockerfile`'s
   header said "the repo has no golden CI job yet"; it now names the `goldens`
   job. The guard's `AGENTS.md` gave `--ruleset memox-v7` as the default check,
   just above the line on CI that §6 names, while CI runs `memox-v8`: both lines
   now say what CI runs (BE-D3's rule: fix the stale part a package touches).
   `dod_check.sh`'s help still describes `--changed` and `--fast` in terms of
   V7's CI; that goes with the planner to BE-D5.
10. **PowerShell 7 on the runner** (Task 4). `ubuntu-latest` has `pwsh`, so the
    eight `LocalPromptHandoffTest` tests, which skip in this container, run
    there for the first time in V8. The scratch run installed PowerShell 7.6.6
    and they passed; on CI the CI tooling tests end `OK` with nothing skipped.
11. **Time** (spec §7, §10). On clean checkouts in this container (4 cores),
    the `gate` job's commands took 1 s (pub get), 87 s (gen-l10n and
    build_runner), 72 s (the from-scratch rebuild) and 217 s (`dod_check.sh`);
    the `goldens` job's took 2 s, 84 s, 10 s (fonts), 182 s (goldens) and 0 s
    (count). `build-apk.yml`'s last run spent 25 s installing Flutter from the
    cache. That is about 7 minutes for `gate` and 5 for `goldens`, run side by
    side. The pull request records the first run's times, job by job (spec §7
    said the plan records them; the plan records the scratch times).

## Review Focus

The inputs and conditions the spec implies that are most likely to bite, each
pinned where it can be:

1. **A job that fails, is cancelled or is skipped**: `CI gate` turns red and
   prints that job's result; it never passes — Task 3,
   `test_ci_gate_is_green_only_when_every_job_succeeded`.
2. **A job added to the workflow later**: `CI gate` must wait for it too, or it
   could fail without blocking a merge — Task 3,
   `test_ci_gate_judges_every_other_job_whatever_happened_to_it`, which requires
   `needs` to name every other job.
3. **A report renamed on one side** (the golden run writes one file, the count
   reads another): the job fails and names the file — Task 3,
   `test_the_goldens_job_compares_the_pictures_and_counts_them`, and Task 2,
   `test_a_missing_report_fails_and_names_it`.
4. **A golden suite that shrinks without failing** (a golden file loses its tag
   or moves out of `test/`): the count fails under the floor, counting only the
   tests that ran — Task 2, `test_a_count_under_the_floor_fails` and
   `test_skipped_tests_and_loading_entries_are_not_counted`.
5. **The runner is not a workstation** (a fresh checkout with no pass stamp and
   no generated code, no git identity, PowerShell 7 present, `python` meaning
   3.13): the gate still passes — Task 4, Step 4 runs the `gate` job's commands
   with `CI=true`; the scratch run added the rest (Clarification 10, "How this
   plan was checked").

def _golden_report(
    root: Path, *, passed: int, failed: int = 0, skipped: int = 0
) -> Path:
    """A report in the shape `flutter test --file-reporter json:<file>` writes.

    Every test file starts with a hidden "loading" test, the reporter's own
    entry, and the run ends with a `done` event: neither is a golden test. A
    failed golden reports `error`, as a failed `matchesGoldenFile` does.
    """
    events: list[dict] = [
        {"protocolVersion": "0.1.1", "runnerVersion": None, "pid": 1, "type": "start", "time": 0},
        {"suite": {"id": 0, "platform": "vm", "path": "test/x_golden_test.dart"}, "type": "suite", "time": 0},
        {"test": {"id": 1, "name": "loading test/x_golden_test.dart", "suiteID": 0, "groupIDs": []},
         "type": "testStart", "time": 1},
        {"count": 1, "type": "allSuites", "time": 2},
        {"testID": 1, "result": "success", "skipped": False, "hidden": True, "type": "testDone", "time": 3},
    ]
    outcomes = ["success"] * passed + ["error"] * failed + ["skipped"] * skipped
    for test_id, outcome in enumerate(outcomes, start=10):
        events.append(
            {"test": {"id": test_id, "name": f"golden {test_id}", "suiteID": 0, "groupIDs": [2]},
             "type": "testStart", "time": 4}
        )
        events.append({
            "testID": test_id,
            "result": "success" if outcome == "skipped" else outcome,
            "skipped": outcome == "skipped",
            "hidden": False,
            "type": "testDone",
            "time": 5,
        })
    events.append({"success": failed == 0, "type": "done", "time": 6})
    report = root / "golden-report.jsonl"
    report.write_text("".join(json.dumps(event) + "\n" for event in events), encoding="utf-8")
    return report


class GoldenCountTest(unittest.TestCase):
    """`count_golden_tests.py` reads the report of the `goldens` CI job.

    A golden run can pass while comparing fewer pictures than it should: a
    golden file that lost its tag, or moved out of `test/`, is simply not
    selected. The floor notices, and only tests that ran are counted.
    """

    @classmethod
    def setUpClass(cls) -> None:
        cls.module = _load("count_golden_tests")

    def setUp(self) -> None:
        temp = tempfile.TemporaryDirectory()
        self.addCleanup(temp.cleanup)
        self.root = Path(temp.name)

    def _count(self, report: Path, floor: int) -> tuple[int, str]:
        out = io.StringIO()
        with contextlib.redirect_stdout(out):
            code = self.module.main(["count_golden_tests.py", str(report), str(floor)])
        return code, out.getvalue()

    def test_a_report_that_meets_the_floor_passes(self) -> None:
        code, out = self._count(_golden_report(self.root, passed=3), floor=3)
        self.assertEqual(0, code, out)
        self.assertIn("golden count floor satisfied (3 >= 3)", out)

    def test_a_failed_golden_fails_whatever_the_count(self) -> None:
        code, out = self._count(_golden_report(self.root, passed=3, failed=1), floor=1)
        self.assertEqual(1, code, out)
        self.assertIn("1 golden test(s) did not pass", out)

    def test_a_count_under_the_floor_fails(self) -> None:
        code, out = self._count(_golden_report(self.root, passed=2), floor=3)
        self.assertEqual(1, code, out)
        self.assertIn("Expected at least 3 golden tests, but only 2 ran", out)

    def test_skipped_tests_and_loading_entries_are_not_counted(self) -> None:
        code, out = self._count(_golden_report(self.root, passed=2, skipped=5), floor=3)
        self.assertEqual(1, code, out)
        self.assertIn("Golden tests discovered: 2", out)

    def test_a_report_with_no_test_fails(self) -> None:
        code, out = self._count(_golden_report(self.root, passed=0), floor=60)
        self.assertEqual(1, code, out)
        self.assertIn("Golden tests discovered: 0", out)

    def test_a_missing_report_fails_and_names_it(self) -> None:
        missing = self.root / "golden-report.jsonl"
        code, out = self._count(missing, floor=60)
        self.assertEqual(1, code, out)
        self.assertIn(f"cannot read the golden report {missing}", out)

def _top_level_block(workflow: str, key: str) -> str:
    """The lines under a top-level `key:` of the workflow, up to the next key."""
    lines = workflow.splitlines()
    block: list[str] = []
    for line in lines[lines.index(f"{key}:") + 1:]:
        if line and not line.startswith(" "):
            break
        block.append(line)
    return "\n".join(block)


def _workflow_jobs(workflow: str) -> dict[str, str]:
    """Each job of the workflow by its key, as the text of its block."""
    jobs: dict[str, list[str]] = {}
    current: list[str] = []
    for line in _top_level_block(workflow, "jobs").splitlines():
        key = re.match(r"^  ([A-Za-z0-9_-]+):\s*$", line)
        if key:
            current = jobs.setdefault(key.group(1), [])
            continue
        current.append(line)
    return {key: "\n".join(lines) for key, lines in jobs.items()}


def _run_script(job: str) -> str:
    """The script of the job's `run: |` step, without its indentation."""
    lines = job.splitlines()
    start = next(i for i, line in enumerate(lines) if line.strip() == "run: |")
    indent = len(lines[start]) - len(lines[start].lstrip()) + 2
    script: list[str] = []
    for line in lines[start + 1:]:
        if line.strip() and len(line) - len(line.lstrip()) < indent:
            break
        script.append(line[indent:])
    return "\n".join(script)

Android: keystore from CI secrets, decoded at build time into a path referenced

must increase on every store upload; both stores reject a repeat. Deriving it
from the CI run number removes the manual step and the duplicate-rejection
round-trip.

`fastlane`, or the store CLIs, from a tag-triggered workflow. Always to internal
testing first, then staged rollout: 10% → 50% → 100%, watching crash-free
percentage between steps. A staged rollout is the rollback plan — a bad release
